# 1. Executive Summary

Packet is a consumer-focused Solana dApp that allows users to create and distribute digital money packets that other people can claim.

A Packet can contain:

* Stablecoins
* Other supported tokens
* A defined number of recipients
* A distribution mechanism
* Optional expiration
* Optional access rules

The fundamental experience is:

> **Create → Drop → Share → Claim**

Packet transforms sending money from a simple one-to-one transaction into a **social, interactive experience**.

Instead of sending:

> "Here is $10."

A user can send:

> 🧧 **$100 Packet — 10 people can claim.**

This makes Packet particularly suitable for:

* Group giveaways
* Community rewards
* Creator giveaways
* Events
* Campaigns
* Social incentives
* Tips
* Promotions
* Token distributions
* Friend groups
* Online communities

---

# 2. The Problem

Digital payments are primarily designed around one-to-one transfers.

Traditional payment interfaces usually look like:

```text
Sender
  ↓
Recipient
  ↓
Amount
  ↓
Send
```

But social money often behaves differently.

A person may want to say:

> "I'm giving $100 to the first 10 people."

or:

> "I'm dropping $50 randomly among everyone in this group."

or:

> "Everyone at this event gets a chance to claim."

Existing payment systems are generally not designed around this interaction.

Packet introduces a programmable distribution primitive:

```text
One funding event
        ↓
Multiple recipients
        ↓
Defined distribution rules
        ↓
Claims
```

# 6. Distribution Modes

## 6.1 Equal

Every successful claimant receives the same amount.

Example:

```text
$100
10 recipients

→ $10 each
```

This should be the simplest Packet type.

---

## 6.2 Random

The total amount is distributed randomly among eligible claimants.

Example:

```text
$100
10 recipients

→ $3.82
→ $17.40
→ $6.13
→ $21.02
→ ...
```

The distribution must always preserve the application's accounting invariants.

The system must never distribute more than the Packet contains.

---

## 6.3 First Come

The first N eligible users receive a predefined amount.

Example:

```text
$50 Packet
10 recipients

First 10 people
→ $5 each
```

# 20. Randomness

Random distribution is one of Packet's most important technical challenges.

A blockchain program cannot safely assume that a simple local pseudo-random function produces unpredictable randomness.

Therefore, production random Packets must use an appropriately secure randomness mechanism.

The exact mechanism should be selected based on:

* security
* cost
* latency
* availability
* integration complexity
* user experience

Aegis should eventually make secure randomness integration easier for applications like Packet.

---

# 21. Security Requirements

Packet handles real value.

Security is therefore a first-class product requirement.

The system must protect against issues including:

* double claims
* unauthorized claims
* unauthorized withdrawals
* over-distribution
* incorrect accounting
* replay-like state issues
* invalid Packet state
* malicious inputs
* race conditions
* incorrect randomness assumptions
* token-account mistakes
* unauthorized administrative actions

The program should be designed so that:

> **The total amount distributed can never exceed the amount legitimately funded into the Packet.**

This invariant should be tested extensively.

# 33. The Relationship Between Product and Framework

Packet should not exist merely to demonstrate Aegis.

It must become a genuinely useful product.

At the same time, Aegis should not be shaped by hypothetical requirements.

Packet gives Aegis real requirements.

Therefore:

> **Packet is the first product that Aegis must earn its way through.**

If Aegis cannot make Packet easier to build, Aegis has failed to deliver its central promise.

If Aegis makes Packet significantly easier to build while maintaining production quality, Packet becomes evidence that Aegis works.

---

# 34. The Dogfooding Rule

Whenever Packet encounters a recurring blockchain-development problem:

1. Determine whether the problem belongs in Aegis.
2. Solve the underlying framework problem.
3. Use the improved framework to solve Packet.
4. Generalize the solution where appropriate.
5. Add tests and documentation.
6. Avoid adding Packet-specific complexity to Aegis unless the abstraction is broadly useful.

This prevents Aegis from becoming a framework built around one application.
